# SpeakMore 实现笔记

给想改代码的人看的：它和 Typeless 原版怎么对应、模型是怎么选的、提示词是怎么调出来的。只想用的话看 [README](../README.md) 就够了。

SpeakMore 是照着对 Typeless 2.8.1 的[逆向分析](../targets/typeless/README.md)做的，只做语音转写这一件事。下面提到的“原版”都指它。

## 用法上照着原版的地方

- 按一下开始、再按一下结束。按住超过 600 毫秒会取消并提示（原版 2.8.1 不支持按住说话）。
- 快捷键可以是任意一个键或两键组合，在设置里录：点一下、按下新组合，一个动作能绑几个（至多 4 个，原版也是）。组合要全部松开才算松开。
- 热键按着的时候又按了别的键，当作组合键处理，悄悄取消。
- 说话的时候按取消键（默认 `esc`）取消；悬浮条上左边取消、右边完成，点完成等于再按一下热键（原版的状态机里也是这几条路）。等成品时取消不了。
- 等成品最多 20 秒；单次录音最长 9 分钟。
- 贴字只有粘贴一条路：存剪贴板、写入带"临时内容"标记的文字、模拟 ⌘V、0.3 秒后恢复剪贴板。
- 麦克风完全没信号时（设备被静音、选错输入）不上传，直接报错。

## 和原版的对应关系

协议照抄抓包看到的消息名和字段名（[05 网络协议](../targets/typeless/docs/05-network-protocol.md#websocketwsrt_voice_flow)），只实现听写用到、并且SpeakMore 的客户端会发的那几条。

| 方向 | 消息 | SpeakMore |
| --- | --- | --- |
| 客户端 → 服务端 | `start_audio` | 只用 `audio_id`，其余字段收下不用 |
| | `set_audio_chunk_info` + 二进制帧 | 序号从 1 开始，按序收；第一块的文件头必须是 Ogg 或 WebM |
| | `end_audio` | 只用 `audio_id` |
| | `set_mode_config`、`replace_audio_context` | 不实现（不采集上下文，只有一种模式） |
| 服务端 → 客户端 | `audio_session_started` | `{audio_id, start_time}` |
| | `received_audio_chunk_count` | `{index, server_t, size}` |
| | `audio_session_ending` | `{audio_id, total_chunks, completed_chunks, failed_chunks}`，这里数的是上传的块 |
| | `audio_processing_completed` | 九个字段与实测相同，听写用不到的五个固定为 `null` |
| | `audio_processing_error`、`error` | `{audio_id, code, detail}` |
| | `debug_info` | 不发 |

和原版不一样的地方：

- **没有登录和签名。** 服务只听本机端口，握手时拒绝带网页来源（`Origin` 为 `http(s)://…`）的连接，防止浏览器里的网页连进来花模型额度。
- **识别和整理是一次模型调用。** 原版服务端内部怎么做的看不到。各块首尾相接后整段发给选的那一家模型（默认 Gemini），Gemini 不用重新编码；OpenAI 不收 Opus，先在本机转成 WAV，见下面[不止一家模型](#不止一家模型)。
- **容器多认一种 WebM。** 原版用自带的编码库出 Ogg；浏览器自带的录音接口出的是 WebM，里面同样是 Opus。服务端按文件头判断是哪一种，实测 Gemini 两种都收。
- **不采集上下文。** 原版会把当前应用、输入框内容、屏幕可见文字一起上传（[06](../targets/typeless/docs/06-context-capture-and-privacy.md)），这里只上传录音。

## 选型时测到的数

测试音频是系统朗读合成的一段 20.7 秒中英混说，带口头禅和一次改口；不是真人录音，结论只能当起点（真实录音的结果见下一节）。耗时是从本机经代理到 Gemini 的整次请求。

| 模型 | 思考档位 | 连接复用后的耗时 | 整理效果 |
| --- | --- | --- | --- |
| `gemini-3.5-flash-lite` | 默认 | 1.2–1.5 秒 | 口头禅删了，改口的痕迹（"不对，应该…"）留着 |
| `gemini-3.5-flash` | `MINIMAL` | 1.6–1.8 秒 | 改口处理对了，"就是说"有时留着 |
| `gemini-3.6-flash` | `MINIMAL` | 1.9–3.6 秒 | 同上 |
| `gemini-3.8-flash` | `LOW` | 2.3–3.3 秒 | 最干净 |
| `gemini-3.8-flash` | 默认 | 6–8 秒 | 最干净，思考用掉了大部分时间 |

原版实测是 `end_audio` 之后 1.4–1.9 秒出成品，所以默认选了 `gemini-3.5-flash`。后来 Google 停用了 3.5 Flash，发给它的请求自动转给 3.6 Flash（官方弃用页；2026-10-14 实测回话报的就是 3.6），默认值也就直接改成了 `gemini-3.6-flash`：实际用的模型没变，只是名字写对了。上表里 3.6 比当时的 3.5 慢一点，转过去之后的速度见下面"记账"一节的实测。

另外三个结论：

- **分块不用重新编码。** 7 个独立编码的 3 秒 Ogg 流首尾相接，Gemini 能从头识别到尾。
- **不能让模型在没有人声时"什么都不输出"。** 那样写时，3 秒静音 6 次里有 4 次编出了一句话。改成输出固定标记 `<无人声>` 后，静音和噪声各 6 次全部输出标记，服务端再把标记换成空字符串。
- **慢的只有进程里的第一次。** 第一次整理要 3.4–4.1 秒，之后稳定在 1.7–1.9 秒，闲置 70 秒和 180 秒后再测也一样，连接没有断。所以服务端只在启动时发一个最小的请求预热，不在每次录音前预热。这一步顺带验证了 key，无效时启动日志里会有 `warm_up_failed`。
- **要求 JSON 输出会让整理变差。** 用 JSON 字段表达"有没有人声"时，模型不再处理改口，所以没有采用。

## 用真实录音调过之后

2026-10-13 用作者自己 Typeless 历史里的 60 条真实录音（2026-08 之后的，2 秒到 121 秒）调了提示词，原版当时的成品当参照。

先核对了原版的排版规律（2853 条成品的统计）：62% 有换行，几乎都是空一行分段；15% 用了 `1.` 这种编号列表，列表前有一句以冒号结尾的话，项与项之间不空行；没有粗体和标题。跟时长强相关：10 秒内几乎不换行，20–40 秒 83% 分段，40 秒以上几乎全分。近两个月以陈述句收尾的成品有八成多不带最后那个句号。

| | 写坏的成品 | 原版分段的 38 条里也分了 | 原版用列表的 16 条里也用了 | 耗时中位 |
| --- | --- | --- | --- | --- |
| 调之前 | 10 条 | 6 条 | 0 条 | 2.1 秒 |
| 定稿（跑了 5 遍，每遍 60 条） | 0–1 条 | 33–35 条 | 7–9 条 | 1.9–2.0 秒 |

原版没分段而这里分了的是 0–3 条（共 22 条），原版没用列表而这里用了的是 0–1 条（共 44 条）。5 遍里后 2 遍是最终版，前 3 遍只差一条"列表从 1 开始编号"的规则。

"写坏的成品"指一眼能看出不对的：开头多出一个不相干的外文词、只输出了开头一小截、中间一长串下划线、整段写成繁体、正文里夹着时间戳。改了这几处：

- **不再把温度设成 0。** 只去掉这一项，同一批录音写坏的就从 10 条降到 5 条，截断和下划线没再出现。
- **录音后面跟一句文字。** 只给录音时成品开头偶尔会多出一个外文词，加上之后少了很多。
- **提示词加了排版规则和三个长例子**（分段、列表、隔了几句才改口）。
- **剩下压不住的在代码里兜底**：繁体字转成简体（[opencc-js](https://github.com/nk2028/opencc-js)）；开头多出的外文词去掉；成品里夹着时间戳就重新请求一次；最后一个句号去掉。前两条规则拿原版 2853 条成品验过误伤：分别是 0 条和 1 条。

还比不上原版的地方：

- **专有名词和人名会听错。** 原版会把当前应用和屏幕文字一起上传当上下文，这里只有录音。去掉标点后和原版成品的文字相似度，5 遍的中位在 0.80–0.82 之间。
- **列表用得比原版少。** 没说"第一、第二"但并列了几件事的话，原版更常整理成列表。
- **口吃偶尔删不干净**，约每 60 条 1 条。最常见的是单字的结巴（"要要做"）：2026-10-15 把它写进规则和例子，一段带"要要"的录音 30 次里从 6 次降到 2 次，没断根。思考档位调到 `LOW` 也断不了根（同一段 40 次里还有 2–6 次），耗时中位还多 0.3 秒左右，所以没改默认档位。也不在代码里删：原版 2888 条成品里单字重复的 42 处大多本来就对（"现在在跑""主要要汲取""不要要求""有有效期""用不了了"）。

### 本地转写链路的润色（2026-10-16）

同样那 60 条录音，先用 Qwen3-ASR 0.6B Q8 在本机各转写一次，之后每个提示词版本都拿这同一份原文交给 DeepSeek 润色（`SPEAKMORE_MODE=local` 跑 `eval-prompt.mjs`，候选用 `--polish-prompt` 传进去，不改源码）。每个版本跑两遍，因为同一个版本两遍之间也有出入。

| 润色提示词 | 原版分段的 38 条里也分了 | 原版用列表的 16 条里也用了 | 写坏的成品 |
| --- | --- | --- | --- |
| 照搬原生的规矩（2340 字） | 24、21 | 4、4 | 0、1 |
| 精简成四条原则，不带例子（474 字） | 13、13 | 6、5 | 0、0 |
| 四条原则加两个例子 | 14、17 | 4、6 | 0、0 |
| **照搬原生的规矩，分点那条写重、加一个步骤例子（定稿）** | 25、21 | 7、6 | 0、0 |
| 照搬的规矩，换 DeepSeek V4 Pro | 21 | 4 | 0 |
| 定稿的规矩，换 DeepSeek V4 Pro | 23 | 5 | 0 |

- **细则在起作用，例子不是束缚。** 精简成几条原则后分段少了近一半，口头禅和重复也删得更差；带不带例子的差别在两遍之间的出入以内。
- **差距不在模型大小。** 换 V4 Pro 分段和列表都没多，润色耗时中位从 0.8 秒变成 1.3 秒。纯文字模型面对一长串没有停顿的转写，不太敢重新组织；原生链路听得到停顿，同样的规矩下分段 34/38、列表 8/16。
- **不开思考。** 作者定的：速度优先。
- 定稿还比不上原版的地方：列表项不提炼"主题："；口语收得不如原版紧；同一条录音有时出编号列表，有时写成"第一，……第二，……"的段落。
- 照搬的那版有一遍出了一条只写到半句就停的成品（结束原因是正常的 `stop`）。

### 本机模型按需装载（2026-10-22，GitHub PR #14）

设置里的 `localModelMemory` 默认常驻；选了空闲 1、5、10、30 分钟后释放（`1m`…`30m`）时，转写模型不在启动时装，状态停在 `idle`。

- **开口时装，说完时等。** `start_audio` 时服务端调 `prepare`，`app/service.mjs` 在这时开始装，不等它；说完整理时转写器等这次装完。装载和说话同时进行，实测松开到出字和常驻差不多（Mac 端到端：第一遍 0.21 秒，第二遍 0.09 秒，常驻 0.10 秒）。
- **空闲从页面最后一条消息起算。** 服务端每收到一条消息调一次 `onActivity`，重新计时：录音时每三秒一块音频，远短于最短的一分钟；取消了就不再有消息，到点自然释放，协议不用加"取消"消息。整理和检查转写器期间另用一个计数挡住，整理比空闲时长还久也不释放。
- **冷启动的数。** Mac（Metal）开机后第一次装 3.5–5 秒，之后 0.4 秒；Windows（i5-13400F）Vulkan 和只用 CPU 都是 1.2–1.9 秒。都在开口时开始，悬浮条等成品的 20 秒没有放宽。
- **没装上不拦热键。** 常驻的装载中、没装上会拦着按热键；按需装载的装载是开口才开始的，没装上的那一次照实报（和常驻同一句"本机模型没装上"），下次开口再装，主窗口照样提示缺本机模型。
- **自定义润色服务不归这里管。** Ollama 0.35 起的 `/v1/chat/completions` 收 `keep_alive`（实测 `"1m"` 留一分钟、`0` 当场卸掉），LM Studio 的请求收 `ttl`（秒，实测 10 秒后卸掉），写在 `customParams` 里就行。PR 原来另调 Ollama 的原生接口续时间、再用计时器去卸，每次润色要多等一个请求，还会卸掉别的应用正在用的同一个模型，没有采用。0.35 以前的 Ollama 在 `/v1` 上不认这个字段，会照常按它自己的默认（5 分钟）卸。

### 语音翻译的提示词（2026-10-22）

翻译是一个任务（`src/server/tasks/translate/`），提示词和语音输入的分开写。目标语言写在提示词第一行，每次说话现拼。让模型先把他的话整理成原文、再译，用 `<原文>`、`<译文>` 两段标签分开：历史里要存原文，先整理再译，改口和口头禅也不会被译进去。

拿 `scripts/dev/eval-translate.mjs` 跑同一批真实录音（eval-prompt 的那 60 条，按时长等距挑 20 条），没有参照译文，好坏靠人看对照表，统计看格式守没守住、原版成品分了段分了点的译文跟没跟上：

| 版本 | 链路 | 格式坏的 | 分点（原版分了点的） | 分段（原版分了段的） | 耗时中位 |
| --- | --- | --- | --- | --- | --- |
| v1：只写规矩 | 直出 Gemini 3.6 Flash | 0/20 | 3/5 | 9/13 | 2.6 秒 |
| v1 | 混合 本机 Qwen3-ASR → DeepSeek | 0/20 | 0/5 | 2/13 | 1.3 秒 |
| v2：分段分点照语音输入写重，配三个例子 | 直出 | 0/20 | 3/5 | 11/13 | 2.6 秒 |
| v2 | 混合 | 0/20 | 2/5 | 6/13 | 1.3 秒 |

- 译文都通顺、像英语母语的人写的，没有漏译和编造。直出把原文和译文都写出来，输出 token 中位 90 左右，比只写译文多一倍，Gemini 那边多等不到一秒。
- 例子里的目标语言是英语，译成日语时（各 10 条）没有被带偏：直出分点 2/3、分段 5/6，混合 2/3、3/6。
- 混合方式的分段分点仍然弱于直出，和语音输入那边纯文字模型"不敢重新组织"是同一个毛病（见上一节），第一版先这样，按他用下来的反馈再调。

两台电脑上的验收（10-22）：

- **端到端**（`scripts/dev/e2e.mjs`，`SPEAKMORE_E2E_ACTION=translate | upgrade`）：Mac 直出译英文松开后 3.7 秒出字，先按语音输入再升级成翻译通过，混合译日文 0.9 秒，离线方式被服务端挡下；Windows 开发机混合译英文 1.0 秒、升级译日文 1.7 秒。那台连不上 Gemini（`fetch failed`，网络的事），直出没在 Windows 上跑。
- **截断会让原文不一样。** 端到端默认只录 7.5 秒，那条录音 8.8 秒；升级那条按键多花 110 毫秒，录音截在半句话的不同位置，本机转写出来的原文就不同（"1.5.0"和"1.5.5.0"）。录满 10 秒时直接翻译、升级、语音输入三种按法原文一字不差，升级本身不影响录音。
- **开发窗口**：Mac 上用合成的系统按键和鼠标事件走了一遍（键盘事件经过小帮手，麦克风换成录音文件）：悬浮条左边的语言胶囊靠鼠标悬停展开（窗口忽略鼠标、转发移动事件），选日文后这一次按日文译，"翻译中"，译文贴进文本编辑，历史和 `speakmore history` 记着功能、语言和原文。作者本人在 Mac 和 Windows 上各真按真说过。
- **Windows 的菜单栏。** 作者在记事本里按右 Alt+空格，窗口菜单没弹（V27），但菜单栏被选中了。单按右 Alt 的语音输入一样，是小帮手插掩码的时机不对，修法见 `docs/hotkey-research.md` 4.2 的掩码一段。

### 划词翻译（2026-10-22）

选中文字后按右⌥回车（Windows 右 Alt+回车），在选区下方弹一张卡片：译文和复制。卡片上原来还有"替换选中文字"（选区能改时把译文贴回原处），10-23 他定了砍掉：划词多半是在网页、App 里看东西，选区不一定能改，往原处贴会出各种问题。小帮手判断"能不能改"的那部分也一起删了。和语音的两个功能是两套：

- **内核**在 `src/server/lookup/`（提示词、收尾、判断原文语言、翻译器、出厂模型），和语音的任务（`src/server/tasks/`）互不引用，只共用底层的 `src/server/chat/client.mjs`。账照记，用途是 `lookup`，历史库因此升到第 4 版（退回办法在 `src/storage/history.mjs` 文件头）。首页的口述统计不算它。
- **设置**是划词自己的四项：`lookup.to`、`lookup.model`（出厂 DeepSeek V4.1 Flash）、`lookup.customUrl`、`lookup.customParams`。选自定义服务时 key 另存一把（`lookupcustom-key.bin`，环境变量 `SPEAKMORE_LOOKUP_CUSTOM_API_KEY`），和语音那边的自定义服务不相干；清单里厂商的 key 同一家只有一把，两边共用。主窗口里在设置的"划词翻译"一栏改译成，在引擎页的"划词"一段换模型、配自定义服务（先验再存，`src/app/lookup/setup.mjs`）。
- **取选区**归小帮手（`selection` 命令）：Mac 先问辅助功能（选中的字和它在屏幕上的框），问不到再模拟 ⌘C 取剪贴板、取完放回原样；Windows 先问 UI Automation，再模拟 Ctrl+C。实测记事本、Edge 都是 UI Automation 拿到的，1–20 毫秒。
- **卡片不抢焦点**：用户正在看、正在写的那个应用留着焦点和选区。卡片窗口做法同悬浮条，透明、点不到，按钮上的点击由小帮手截下来交给主进程（截的时候顺带报"点在卡片外面"，用来收起）。
- **语音输入的键是划词组合的一部分**（右⌥ 和 右⌥回车）：按下右⌥ 时先压住，见 `docs/hotkey-research.md` 的 5.3，悬浮条不会闪一下。

提示词改了几轮。他第一次真按时说译文"一股机翻味道"，于是在提示词里写明中文要像中文作者自己写的（不照搬英文语序、少用"进行""被"、长句拆开），配三个例子。"选中的已经是目标语言"一开始交给模型判断，DeepSeek V4.1 Flash 不可靠：中文原文、目标中文时它改写中文；英文原文、目标英语时照抄；在用户消息里写上"已经是就译成英语"，英文原文、目标日语时又译成了英语。所以改由代码判断（`src/server/lookup/source.mjs`）：文字系统认得出的（中日韩、俄文、阿拉伯文、泰文，繁简另看）发请求前就认出来，英语看虚词占的比例；别的拉丁字母语言先照常译，译出来和原文几乎一样再改译一次。中文目标遇上繁体、日文汉字这种要转写的，认出"不是"就作数，不再比译文像不像原文：转写前后八成字相同，一比就当成照抄、改译成了英文（10-23 审查查出）。中文里夹的英文按词算，不按字母算。是目标语言时改译成英语（目标是英语时改译成简体中文），卡片上写实际译成的那种。

拿 `scripts/dev/eval-lookup.mjs` 跑 18 条造的句子（英译中、中译英、已是目标语言的、繁体、单词、报错、列表、日语、法语），每条两遍，好坏由人看：

- 定稿那版、DeepSeek V4.1 Flash：语言 36/36 对，意思都对，中文读着不像机翻。每条耗时中位 0.87 秒，最快 0.53 秒、最慢 1.04 秒。日语那条第一遍语气偏了一点（"にすぎない"），第二遍对。单词给最多三个义项（bear：熊；承受；忍受）。提示词的规矩里举了 "the other half of the story" 怎么译，评测里正好有含这句的一条，那条不算独立的检验。

## 不止一家模型

录音交给哪一家整理是一个策略：每家一个适配器，管"请求怎么拼、收哪些录音格式、报错怎么认"；提示词、收尾（繁转简、去句号、夹时间戳重来）、转格式是各家共用的一条流程。

```text
设置里的 model（openai/gpt-audio-mini）
   │
   ▼
src/server/providers/index.mjs   厂商清单：名字、key 的环境变量、申请页、默认模型、有没有思考档位。不加载 SDK
   │ load()
   ▼
providers/gemini.mjs、openai.mjs 适配器：ping()、generate()、AUDIO_TYPES、classifyError()
   │
   ▼
src/server/refine/refiner.mjs     共用的流程：这家不收录音的格式就先转（src/server/audio/），拿原文，统一收尾
   │                              出错一律抛 ModelError，分成 key / unavailable / other 三类（providers/errors.mjs）
   ▼
src/server/server.mjs             听写协议那一侧不知道背后是哪一家
```

每家一把 key，存成 `<厂商>-key.bin`；Gemini 的文件名和以前一样，所以不用迁移。设置里的 `model` 写成 `厂商/模型`，以前只写 Gemini 模型名的照样认。

加厂商的规矩：作者点名要哪家才加。2026-10-13 先查了 DeepSeek：官方文档里它的对话接口只收文字、图片和文件（文件也只认图片格式），没有收音频的地方，也没有单独的语音识别接口，所以没接。除了 Gemini，官方文档写明能"收音频、按提示词一次出成品"的是 OpenAI（`gpt-audio` 系列）和阿里通义（Qwen-Omni）；作者选了先接 OpenAI。

### OpenAI 那边实测到的

用的是作者的实验用 key，2026-10-13 从西雅图测的。录音是作者自己用 SpeakMore 时的 6 段测试录音（1.7–33.7 秒），没有用 Typeless 的历史录音（发给 OpenAI 这件事没问过作者）。

- **只收 wav 和 mp3。** 传 webm、ogg 都回 400："Supported values are: 'wav' and 'mp3'"。悬浮条录的是 WebM（Electron 的录音接口录不了 Ogg，实测 `MediaRecorder.isTypeSupported("audio/ogg;codecs=opus")` 是 false），所以服务端先解码（[@audio/decode-webm](https://www.npmjs.com/package/@audio/decode-webm)）、降到 16 kHz、封成 WAV。降采样和封 WAV 是自己写的（`src/server/audio/pcm.mjs`），一分钟的录音约 60 毫秒。
- **采样率要降。** 同一段 90 秒的录音，48 kHz 的 WAV 要 18 秒，24 kHz 和 16 kHz 是 6–9 秒；三种算出来的音频 token 一样多（907），所以降采样只省上传、不省钱。
- **验证 key 不能发纯文字。** 这几个模型要求输入或输出里有音频，纯文字的请求回 400；所以带一段 0.1 秒静音、只要 1 个 token，约 0.7 秒。
- **报错**：假 key 回 401 `invalid_api_key`，写错的模型名回 404 `model_not_found`，都按实测写进了分类。账号没额度（429 `insufficient_quota`）、所在地区不支持（403 `unsupported_country_region_territory`，归成"暂时用不了"、提示查代理，不叫人换 key）照官方文档的错误码写的，没测到。
- **长录音慢。** WAV 比悬浮条录的 Opus 大七八倍，一次请求最多等 30 秒、包括上传；悬浮条那边等成品最多 20 秒（照原版）。按 90 秒的录音要 6–9 秒推算，三分钟以上的录音交给 OpenAI 可能等不到，录音会留着。没实测；要改的话可以换成 MP3（要多一个编码库）或者给 OpenAI 放宽等待。
- **选哪个模型。** 同 6 段录音、同一份提示词：

  | 模型 | 结果 | 耗时 |
  | --- | --- | --- |
  | `gpt-audio-mini` | 6 段都正常，静音那段输出了 `<无人声>` 标记；口头禅偶尔留着（"就是"） | 1.9–4.9 秒 |
  | `gpt-audio-1.5` | 两段把成品包成了 `{"final_text": "…"}` 或 `{"…"}`，两段开头多了换行；另一次同一段录音回了 500 "The model produced invalid content" | 1.7–4.1 秒 |

  所以默认用 `gpt-audio-mini`。提示词是对着 Gemini 调的，没拿成批的真实录音对 OpenAI 调过，作者定了边用边调。Typeless 的历史录音只发给 Gemini，而且它们是 Ogg：拆 Ogg 要用 LGPL 的 codec-parser，作者定了不随程序分发，所以服务端只把 WebM 转成 WAV，Ogg 交给 OpenAI 会直接报错。

### Gemini 的回归

换成策略之后 Gemini 的请求和以前一样。同一批 60 条 Typeless 录音又跑了一遍（v8），和之前同一份提示词的两遍（v7-1、v7-2）比：

| | v7-1 | v7-2 | v8 |
| --- | --- | --- | --- |
| 成功 / 写坏 | 60 / 1 | 60 / 0 | 60 / 0 |
| 文字相似度中位 | 0.80 | 0.82 | 0.80 |
| 原版用列表的 16 条里也用了 | 7 | 9 | 7 |
| 耗时中位 | 1.9 秒 | 1.9 秒 | 2.3 秒 |

v8 在前两遍之间。耗时多了 0.4 秒，原因没查实：每次请求的代码路径没有多出步骤，两次测的时候网络环境可能不一样。

## 记账：花了多少钱、多少 token、等了多久

原版是包月的，不需要这一项；这里每次调模型都按量收费，所以每一次回了话的调用都记一笔账。

```text
providers/gemini.mjs、openai.mjs        从回话里取用量，按回话报的型号查自家的价目表（providers/prices/）算钱
   │ { model, inputTokens, audioTokens, cachedTokens, outputTokens, thinkingTokens, costUsd }
   ▼
refine/refiner.mjs                      量一下等了多久，记一笔（onCall）：听写的带上 audio_id，验证 key 的算 check
   ▼
src/app/main.mjs → storage/history.mjs  存进历史库的 model_calls 表
   ▼
src/usage/report.mjs                    今天、本月、累计、按型号分开；speakmore usage 和主窗口首页共用这一份
```

规矩和为什么：

- **价格只抄官方价目页的标准档付费价**（2026-10-14 抄的，出处写在 `providers/prices/` 两个文件的开头）。Gemini 在免费档里用不收钱，可接口不告诉我们这把 key 在哪一档，所以一律按付费价估算，界面上写明是估算。价目表里没有的型号 token 照记，钱写"价格不明"，不混进花费。
- **按回话报的型号算钱，不按请求的。** 实测请求 `gemini-3.5-flash`，回话里的 `modelVersion` 是 `gemini-3.6-flash`：官方弃用页写着 3.5 Flash 已停用，请求自动转给 3.6 Flash。3.6 Flash 不分文字和音频，输入 $0.75、输出 $3.75 每百万 token，2027-01-01 起翻倍；价目表按调用那天取价。OpenAI 回话报的是带日期的快照名（`gpt-audio-mini-2025-12-15`），去掉日期查价。
- **用量字段对着实测的回话写。** Gemini 的 `promptTokenCount` 含音频；思考的 token 单独报在 `thoughtsTokenCount`，不在 `candidatesTokenCount` 里（开 HIGH 实测：提示 26、输出 1、思考 179，合计 206），输出价按两者之和算；不思考时回话里没有这一项。OpenAI 的 `prompt_tokens_details` 分得出文字和音频；gpt-audio 系列的缓存价一栏是"-"，命中缓存也照原价算。
- **回了话但用不了的也记。** 被截断、被拦下的回话是收了钱的，所以适配器不再自己抛这类错，带着用量交回去，由整理流程记完账再报错。
- **没回话的记不了。** 用量只在回话里，没回话就没有数。连不上的请求没发出去，本来就不收钱；发出去了却等不到回话的（30 秒超时、听写服务关掉时断开）对方可能已经算完、照样收钱，账上会少这一笔，收没收没法知道（没验证），所以只在日志里记一条 `model_call_unmetered`。悬浮条上按 `esc` 取消发生在交出录音之前，不会碰到这种情况。
- **记账出错只写日志**，不能因为少记一笔把用户的这句话丢掉。
- **等了多久量的是发出请求到收齐回话**，不含本机转格式（交给 OpenAI 前那一步，一分钟的录音约 60 毫秒）。一次听写重来过的，几次加在一起才是用户等的；报表给中位数（"一般"）和九成分位（"慢时"）。
- **账存在历史库里**，库的版本从 1 升到 2，旧库打开时自动升上来。退回 0.4.2 之前要先降回去（命令写在 `src/storage/history.mjs` 的 MIGRATIONS 注释里），只丢账，不丢历史。

一次听写多少钱（合成的 5 秒语音，两家各走一遍端到端）：

| | 输入 token（其中音频） | 输出 token | 花费 | 模型用时 |
| --- | --- | --- | --- | --- |
| Gemini（实际是 3.6 Flash） | 1500（135） | 18 | $0.0012 | 3.4 秒 |
| OpenAI `gpt-audio-mini` | 1576（54） | 19 | $0.0015 | 2.7 秒 |

钱的大头是每次都带上的提示词：Gemini 那边光提示词就有 1365 个 token，占了这一次花费的八成多。所以接着做了提示词缓存。

### 提示词缓存

- **隐式缓存用不上。** Gemini 2.5 以后默认开着隐式缓存，命中的部分只收一成的价，但 3.6 Flash 要提示词前缀至少 4096 个 token 才会命中（[官方缓存文档](https://ai.google.dev/gemini-api/docs/caching)），我们的提示词 1350 个（`countTokens` 实测），上面几次一次都没命中。
- **显式缓存可以。** 实测在 3.6 Flash 上拿这 1350 个 token 建得起来（没被门槛拦下）；带着它的请求，回话里 `cachedContentTokenCount` 是 1350，成品一字不差。带缓存时不能再写 `systemInstruction`（实测 400），思考档位照设。缓存没了时回 403 "CachedContent not found (or permission denied)"。建一个约 0.7 秒，续一次约 0.4 秒。
- **怎么收钱。** 带缓存的请求里那 1350 个 token 按缓存价（3.6 Flash 是 $0.075 每百万，一成）；存着按小时收存储费（$0.50 每百万 token 每小时，2027 年起翻倍）；建的时候按标准输入价收一次——这一条是 [Vertex AI 的缓存文档](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-overview)写的，Gemini API 的文档没说，按同样的算，**没验证**。存储按设的时长收、删早了不退，是社区里的说法，也没验证，所以账上记的是买下的时长。
- **什么时候建、放多久。** 开口说话（`start_audio`）时建，已经有了就往后续；说完整理时带上。建要 0.7 秒，录音一般好几秒，所以第一句话也用得上。放多久拿作者在原版上 126 天、3169 次听写的时间间隔（中位 3 分钟）模拟过，只算提示词那部分的钱：

  | 没人说话多久后过期 | 建了几次 | 存了多久 | 提示词的钱省多少 |
  | --- | --- | --- | --- |
  | 5 分钟 | 1339 | 152 小时 | 45% |
  | 15 分钟 | 828 | 324 小时 | 57% |
  | 30 分钟 | 587 | 496 小时 | 61% |
  | 60 分钟 | 391 | 734 小时 | 62% |

  取 30 分钟：再长省不了多少，空存着的时间倒是更长。隔很久才说一句的话（建一次只用一次），这一句反而比不缓存贵约两成。
- **出岔子都退回原样。** 缓存没了就照原样再发一遍；型号建不了（4xx，比如 4 Argon 起只有隐式缓存）就不再试；建不好只记警告。缓存只是省钱，不能耽误这一句话。
- **OpenAI 没做。** `gpt-audio-mini` 同样的请求连发 3 次、带上 `prompt_cache_key`，`cached_tokens` 都是 0，价目表上它的缓存价一栏也是"-"。

实测（合成的 5 秒语音，端到端）：开口时建缓存 0.74 秒，这一笔 $0.00135（建 $0.00101 加存 30 分钟 $0.00034）；接着那次整理命中 1350 个 token，花费从 $0.0012 降到 $0.00028，成品一样。再开口时只续期，连着两次续期之间那两秒的存储费不到 $0.000001。

## 界面：主题、窗口和悬浮条

**主题是数据，不是代码。** 三套主题只在颜色的值上不一样，没有哪一套要有自己的行为，所以没有做成“每套主题一个带方法的对象”。做成的是一份约定加一张登记表：

- `src/themes/contract.mjs` 列出界面要的全部颜色：悬浮条 10 个，窗口 12 个（浅色深色各一份）。界面只认这些名字，不知道现在用的是哪一套。窗口里有三个是为观感加的：`glow` 是渐变的另一头（主按钮、键帽、进度从 `primary` 走到它），`aura`、`aura2` 是窗口背后的两团光。
- 每套主题是一个文件，一份符合约定的数据；`index.mjs` 是登记表。加一套就是加一个文件、登记一行。
- 合不合格机器说了算（`themeProblems`）：缺了哪个、多了不认识的、颜色写法不对、该读得清的地方对比度不够（字 4.5、图标和色块 3），都指得出是哪一个。为了让对比度算得了，颜色只认 `oklch(亮度 彩度 色相)` 一种写法。渐变两头都要托得住主按钮上的字，光晕最浓的地方也要托得住正文和次要的字。
- 这一层不依赖 Electron，也不依赖 Node。命令行用它列主题、在终端里画出颜色，主进程用它生成 CSS。

**颜色怎么到页面上。** 页面的样式里一个颜色都不写，只用 `var(--…)`；值由预加载脚本注入。它一上来就同步向主进程要现在这套主题的 CSS，用 `webFrame.insertCSS` 放进页面，这发生在页面的第一个脚本运行之前（实测过），所以不会先闪一下没有颜色的样子。换主题时主进程给每个开着的窗口再发一份，先放上新的再撤掉旧的。命令行换主题走控制通道的 `reload-theme`，不重启。

样式和主题之间的约定有测试把关（`test/themes/css-tokens.test.mjs`）：主题给的变量样式文件里不重复定义、用到的变量都有出处、主题的每个变量都有地方用、样式里不写死颜色。

**窗口：结构照原版，观感是自己的。** 主窗口（`renderer/hub/`）照原版：左边侧栏切首页和历史记录，设置是盖在上面的对话框，红绿灯藏进侧栏左上角；首次引导（`renderer/onboarding/`）不照原版：开屏 → 功能演示 → 检查快捷键 → 权限（只有 Mac）→ 引擎，不填密钥、不选识别方式、不试说话（密钥都没配，试了也说不出字），最后把人送到引擎页去配；哪一步都能退回、能跳过。观感不照抄原版的灰白：

- 窗口背后铺两团主题色的光（`aura`、`aura2`），一直不动。卡片和列表是半透明的面，透出一点光的颜色，上沿一道亮边。
- 玻璃（`backdrop-filter`）只用在后面真有东西的地方：侧栏（透出光，颜色被提一点）、设置对话框（后面的首页先整体模糊一层）、内容区往下滚时顶上那条拖窗口的地方（滚上去的字在它底下变模糊）。卡片后面只是平滑的光，加模糊看不出区别，就不加。
- 主题渐变只铺在小面积上：开关、进度和电平条。按钮先也是渐变，2026-10-23 改成苹果那样的实色（主要）、淡灰底（次要）。首页的口述卡先是整块铺满渐变（太大太抢眼），后来收成右边一列里的小卡、渐变只留在键帽上；那一列字少却占了一条侧栏的宽，最后整列去掉：热键写在标题下面一行，键帽照实体键画成浅底细边，版本号挪到侧栏底下，首页的卡片占满整宽。
- 灰阶和面的颜色在 `shared/window.css` 里从主题的正文色、底色用 `color-mix` 调出来，换主题、换深浅色都跟着变。热力图的深浅在 oklab 里混：在 oklch 里把主题色和纯白（彩度为 0、色相写的是 0）混，色相会往 0 度拉，朱砂的浅档成了粉色（截图看到的）。
- 系统开了"降低透明度"时，玻璃和半透明的面换成实底。
- 界面上的字是短词短句，细节放进悬停提示。

**悬浮条分三层。** `bar-view.mjs` 由状态机的状态算出该是哪种样子、提示怎么写（纯函数，有测试）；`bar-ui.mjs` 加 `bar.css` 把样子画出来，要宿主代办的只有两件事（显示/收起窗口、截哪几块）；`bar.mjs` 只剩控制。换主题只动数据，换壳只换那两件事的实现。

**为什么点击和 `esc` 不经过悬浮条的窗口。** 悬浮条的窗口整个点不到（鼠标事件全部穿过去），它也拿不到键盘焦点。两个按钮的点击和 `esc` 是原生小帮手在事件到达任何窗口之前截下来的：

- 试过让窗口自己收点击。Electron 的 `panel` 类型窗口加 `focusable: false`，点一下，最前面的应用还是从原来那个变成了我们（实测）。焦点一走，文字就贴不回原来的输入框。
- 原版也是 Electron，它的做法是点了之后用 AppleScript 把原来的应用重新切回最前面。这样原来的窗口会闪一下，而且要多一项“自动化”权限。
- 所以这里换了一条路：小帮手另开一个能改事件的监听（要辅助功能权限），平时关着，只在说话的时候打开，吞掉 `esc` 和落在两个按钮范围里的鼠标按下、松开，报给主进程。别的事件原样放行。没有辅助功能权限时这个监听建不起来，悬浮条就不画那两个按钮，提示里也不提 `esc`。
- `esc` 必须吞掉而不是只听：不吞的话，取消听写的同时前台应用也会收到它，对话框会被关掉，终端里正在跑的东西会被打断。
- 几道保险：条收起来、页面崩了时主进程都会再说一遍“不截了”；小帮手截了 10 分钟没人管就自己松开。`esc` 一直被吞掉的话，在哪个应用里都按不出来。
- 踩过的坑：自己关掉监听时，回调同样会收到“监听被停掉了”的通知。在那里再关一次，就会没完没了地收通知、空转。

**快捷键：一张动作目录，匹配和吞键在小帮手里。** 调研和每个决定的来由在[热键调研报告](hotkey-research.md)，这里只记结论：

- 能按快捷键做的事列在 `src/hotkeys/actions.mjs` 一张表里（现在是语音输入、语音翻译、划词翻译和取消）。设置项 `hotkey.<动作>`、环境变量、命令行、设置页的每一行、状态、下发给小帮手的绑定表，都按它生成。
- 键用 W3C 的 `KeyboardEvent.code` 名字，和两个系统原生码的对照只在 `src/hotkeys/keys.mjs`。主进程把组合换成原生码，用 `bind` 发给小帮手；小帮手按"现在按住的键的集合"精确匹配，只报"哪个绑定按下、松开、被打断"。
- 组合里的普通键要吞掉，不然 `右⌥ 空格` 开始听写的同时前台会多出一个空格。macOS 上能改事件的监听平时关着：一个只收修饰键变化的监听在同一个回调里把它打开，按住修饰键后的第一个普通键就能拦下（只在事后打开会漏，实测人按得出 0.4 毫秒的间隔）；单个 F 键走 Carbon 热键。Windows 的键盘钩子本来就能吞；Alt 或 Win 按住期间触发了绑定、吞了键，就补按一个无用的键，免得松开时弹出菜单栏或开始菜单。
- 和系统、常用快捷键撞的组合直接不让绑（`src/hotkeys/validate.mjs`）：宁可少开放几个键，也不要绑上以后到处误触发。别的应用自己注册的查不全，录键时问一下系统（macOS 的系统快捷键表、Windows 试登记一次），撞了同样不存，说是被系统还是别的程序占了。命令行 `config set` 查不了这一项，只按静态的表拦。
- 录键也在小帮手里：只在主进程说"录"之后、到说"停"或 30 秒到点为止报按住了哪些键码，不报字符；按键吞掉，不进前台应用。什么时候定稿、定成什么在 `src/hotkeys/record.mjs`：按住的键数第一次变少时，定成此前按住最多的那一组。
- 0.13 以前存的是一个键的 id（`right_option` 之类），只在入口认：第一次启动时换算设置文件，`SPEAKMORE_HOTKEY`、`config set hotkey` 照样能用。换算和对照表在 `src/storage/legacy.mjs`、`src/hotkeys/legacy.mjs`。退回旧版时它读不到新设置，用默认键起来。

设置文件开头带 BOM（Windows PowerShell 5.1 的 `Set-Content -Encoding utf8`、老版记事本存出来的都带）时，0.14 及以前读不出来、App 起不来（2026-10-21 在 Windows 上验收时碰到）；0.15 起读之前先去掉。

还没做的：悬浮条固定在主屏幕底部（原版每 100 毫秒看一次鼠标在哪块屏幕上，跟着换）。

## 安装和运行环境

目标是一行命令装好并启动，装的人不需要 Node、npm、Xcode，装的和产生的东西都在 `~/.speakmore` 一个目录里。

- **运行环境是包里自带的原版 Electron，命令行也用它跑。** Electron 里本来就有一个 Node，设上 `ELECTRON_RUN_AS_NODE=1` 它就当普通的 Node 用（VS Code 的 `code` 命令是同一个做法）。这样只带一份运行环境，不依赖系统里有没有 Node、是哪个版本。实测 Electron 44.7 里是 Node 24.21，带着 `node:sqlite`；跑 `speakmore --version` 要 41–43 毫秒，系统的 Node 26 是 51–57 毫秒。
- **发布包自带一切。** `scripts/release/release.mjs` 在打包的机器上把运行时依赖装好、小帮手按两种芯片编好合成一个文件，再配上对应芯片的 Electron，打成 `speakmore-darwin-<芯片>.tar.xz`（Apple 芯片约 92 MB、Intel 约 100 MB；0.10.1 以前是 tar.gz，约 135 MB）；更新不下这个包，只照清单下本机缺的块（见[开发说明](development.md)的下载地址一节）。Electron 的压缩包按 `electron` 这个 npm 包里带的校验值核对过才用。
- **发布包放在自己的下载地址上，不用 GitHub Release**（那边在国内太慢）。腾讯云 COS 的一个私有桶，前面挡一层 CDN（`dl.zephyrxiang.com`），桶只让 CDN 读。上面的样子定在 `src/update/layout.mjs`：更新用的块和清单在 `store/` 下、按内容命名，每个版本首次安装用的包在各自的目录里，传上去就不再变（长期缓存）；根上的 `install.sh`、`install.ps1` 和 `channel.json`（最新的版本号和每种装法的清单）每次发布会换，只缓存一分钟。上传时先传块、再传包和安装脚本，最后才换 `channel.json`，所以任何时刻照着它去取，要的东西都已经在了；同一个版本号已经在上面而内容不一样时拒绝覆盖。发布只从作者的电脑上发（`npm run ship`），0.4.0 起不再由 CI 发。
- **安装脚本只做搬运。** `install.sh` 先做预检查，下载后核对 SHA-256，解到家目录里的临时位置并原地试跑一次，都没问题才停掉正在运行的、把 `app/` 和 `runtime/` 换进去。两样要么都换成，要么都不换。
- **启动脚本里的路径是写死的。** `~/.speakmore/bin/speakmore` 由安装脚本生成，家目录的位置直接写在里面：它会被 `~/.local/bin` 里的链接指着，不能靠“我在哪”来猜。
- **目录以外的东西有清单。** 安装时在别处建的链接记在 `bin/links` 里，卸载时照着删，删之前再确认一遍它还指着我们。删不了的（记在终端名下的系统权限、所有原版 Electron 程序共用的 `com.github.Electron.plist`）在卸载时列出来。
- **权限仍记在终端名下。** 后台应用是命令的子进程，系统把麦克风、输入监控、辅助功能算在启动它的终端头上。好处是升级不用重新授权；坏处是系统设置的列表里看不到“SpeakMore”这个名字。想换成记在应用自己名下，要把它做成一个有固定签名的应用，这留到以后做桌面端时一起解决。
- **退回 0.1 版**：0.1 版的数据在 `~/Library/Application Support/SpeakMore`。这一版第一次运行时把其中的历史、录音、设置、加密后的 key 搬进了 `~/.speakmore`（历史和录音在 `data/` 下）。要退回，把这几样搬回原处即可；历史里记的录音位置会指着新地方，只影响失败记录里“录音留在哪”那句话。

还没做的：Windows 上程序路径带空格时（比如用户名里有空格），App 设置里的开机启动开着也显示成关着。Electron 44.7 的 `getLoginItemSettings` 拿 Run 里那一项和我们给的程序路径比，路径没加引号、带空格时对不上（2026-10-17 在真机上用带空格的测试目录看到，没验证改法）。
