2026-10-16 用户定的。本地转写的模型广场不替用户做决定，能接的模型都接上，用评测结果给每个模型打标签、写简介（哪种芯片、哪个系统上跑得最好，中文、中英夹杂各什么水平），推荐可以给，选择留给用户。

用户原话："咱们不要去替任何人或者模型做主。咱们测出 benchmark、跑通 pipeline 后，给这些模型打上 tag，加上简介，说明它们在各个场景下的具体表现就行。"

**Why:** 项目有了反响，用户的机器各不相同（已有人 fork 去做 Windows），一个"官方首选"替不了所有人。
**How to apply:**
- 推荐写成"在某种机器上最合适"，不写成唯一答案。例：Apple 芯片上 Qwen3-ASR 0.6B 的 Q8（transcribe.cpp 加 Metal）最准，SenseVoice Q8 最快。
- 标签只来自实测数据，没测过的平台（Windows、Intel）写"未实测"，不按推测打标签。
- Windows 上的原生端到端测试暂时放下，先把能在本机做的做好。
- 评测流程见 bench/README.md，判官是 Claude，见 [[bench-judge-is-claude]]；两条链路的关系见 [[speakmore-two-pipelines]]。

**2026-10-16 又定的结构（扩充到云端模型时）：**
- 百炼走国内站。顶层按角色分：原生（一步）、转写（下分本机、云端）、润色；Key 按平台另放。
- 各家官方的 key 也要单独接，不能只靠百炼：用户原话"很多人是只用一家的，比如说 kimi/deepseek/glm 啥的，虽然百炼也有，但不是同一个 key，所以得单独列出来"，再加上海外用户用不了百炼国内站。同一个模型在几个平台都有时，做一张卡、标出经由哪些平台。
- 模型从设置里搬出来，放到主窗口侧栏，单独一页，"像逛商场一样"。
- 对接口差异的态度："反正就是策略模式，有不同的情况单独拎出来处理就好了……对用户来说不就是填写一把 key 就能直接做了吗……要有用户思维"。百炼里调用方式不统一的部分（转写要用 DashScope 自己的写法）由 SpeakMore 在适配器里处理掉，不让用户感知。
